日期：2026-10-22。审查基线：本地 OpenFix `0742a59`，三个包版本均为 `0.12.4`。下一版本号尚未指定。

## 范围与实际完成情况

用户将原先续写至100章的任务收束至约60章，并要求以真实使用经验查找软件缺陷。本轮已正式保存并回读到59章；第60章初稿及一次定向修订仍不满足验收，保留为失败样本，未批准、未写入正文。61—100章不继续生成。

本文件是下一版本的开发与验收规格，**不代表以下产品修复已经实现**。本轮只做真实调用验收、源码核查及任务记录；没有运行软件测试、lint、typecheck或build，不引用历史通过记录冒充本轮结果。

当前对象是 `新版本/OpenFix` 的 Python/FastAPI Fork，不是根目录另一套 Rust 原型。目标属于长篇一致性与可信候选交付；不借本任务推进全书自治生成、第二套RAG或Runtime重写。

私人小说、模型请求全文和审稿原文留在本地被忽略的验收目录，不进入Git。公开回归用例应使用合成故事。

## 发布前优先修复

### LF-01 人物状态已存储，但Writer直接读取链路不完整

**分类：已证集成缺口。影响：高。**

现状：

- `backend/app/agent_runtime/tools/impls/context/character.py:218` 的契约明确是读角色描述；`:222` 仅返回`name/description`。
- `backend/app/retrieval/story_memory.py:148` 已把人物profile和最新CharacterState合入索引，不能报告为“人物状态没有实现”。
- `backend/app/agent_runtime/tools/impls/context/narrative_state.py:99` 和 `backend/app/core/narrative_context.py:246` 读取世界事实、人物信念、情节线、场景计划；不等于读取原有CharacterState。
- 本轮用一个人工维护的短世界条目补充当前状态，属于验收补救，不能作为产品能力完成证明。

**最小修复边界：** 复用人物扩展repo和现有只读工具，提供有预算的相关角色状态读取。结果明确区分静态profile、章级state、人物belief、世界fact；标明来源章、适用时间和未记录项。保持现有`read_character`调用兼容，可扩展可选范围或独立小工具，不复制存储/RAG。

**验收：**

1. 合成角色静态档案称其擅长搬运，当前state为肩伤；Writer实际请求中可验证出现当前state及来源。
2. 回改早章时，不把后章的死亡、能力或认知灌入；没有对应时间状态时显示未知，不默认最新即正确。
3. 项目隔离、未确认事实排除、Token上限、无state的旧项目兼容。
4. 不把“左手可动”推导成“伤员能单手承受重物/震动”；物理合理性仍需审稿，状态注入不是质量保证。

### LF-02 Plan到Writer的交接会丢要求，也会替作者扩写意图

**分类：本轮轨迹已证的交接失败；实现方案需保持现有编排。影响：高。**

60章外层请求指定的读取要求没有进入实际dispatch；同时Plan把有限意图进一步细化为物件是旧物/捡拾废件、五人具体分工和伙伴愿望示例。应区分已有硬要求和规划示例，不能仅凭dispatch变长就判定新增剧情。仅给主Agent增加一句“必须读资料”，无法证明子Agent收到了它。

**最小修复边界：** 在现有dispatch/Task/Context扩展点保留有类型的短交接数据：当前目标、确认事实及来源、角色状态、未来作者计划、必须保留项、允许修改范围、字数口径。区分硬要求和示例。需要读取的源由确定性上下文步骤解析，或在缺少读取证据时明确标记未完成；不默默把自由文本改写视为等价传递。

不能只保留伤势与禁令：本轮短事实卡也遗漏了此前已凭劳动获得食物的成果，为“第一次挣到吃食”重演创造了条件。近期成果、已兑现承诺、已有资源与未结义务都需要有界承接。

**验收：**

1. 以合成“已换过饭、仅获七天借住许可、关键物件用途未知”为约束；审计能比对请求、实际dispatch和子Agent实际输入。
2. 不把“未知是否安葬”改成已葬，不把借住期限补成未经同意的驱逐/租金条款。
3. 不强制逐章重读全书；来源已在上下文且版本匹配时复用。
4. 已发生事实和未来剧情计划保持独立；合理新增普通情节仍可提出为候选，不因旧资料未列出就全部禁止。

### LF-03 `max_iterations`请求字段未生效

**分类：已证API到执行配置的透传缺陷。影响：高。**

`backend/app/api/schemas/agent.py:19` 接受该字段；`backend/app/api/routers/agent_runtime.py:851` 创建SessionRunner时未传；`backend/app/agent_runtime/runner/session_runner.py:127` 构造器也没有对应参数。不能只向当前构造器加一个不支持的关键字参数。

**最小修复边界：** 从请求、会话持久配置、Runner到ReAct实际停止条件建立一条生效路径。明确恢复会话及子Agent是否共享预算，兼容旧会话默认值。不得只更改schema文案或把图递归限制冒充Agent迭代限制。

**验收：** 请求低上限，实际执行到上限时停止，返回结构化原因；重启/恢复后上限不丢；不会在结束后再次派生无预算子任务。现有`tests/api/test_agent.py:928`附近的上下界校验不是这项行为验证。

### LF-04 定向修订缺少确定性的差异与约束验收

**分类：多次真实候选中的稳定性问题；尚未证明单一根因。影响：高。**

60章修订同时修旧错、引入新错；59章独立模型也曾建议错误的物件归属。60章首审被刻意限制为200—300字、最多3项，报告了锤击支撑、日期和尾段问题，未报告全部已提供的跨章冲突。该结果证明本次受限报告的覆盖不足，不证明模型没有跨章审查能力。模型说“可发”不能替代事实核查。

**最小修复边界：** 复用当前Reviewer、Actor、Diff和Revision，形成候选→诊断→局修→复核。审稿项必须有位置、证据来源、问题类型、修改目标、preserve；事实证据不足时返回不确定。局修后核对变化范围、保留项、时间/资源/伤势等关键约束和候选哈希。修改需要改变Plot时退回规划，不让Actor私自补重要事件。

**验收：**

1. 修称呼不会改变物件归属；修伤员动作不会顺手发明医治或新设备。
2. 定向修订若超长或新增事实冲突，仍为候选并显式失败，不自动保存。
3. 原文/候选/审稿/最终接受内容各自绑定版本和hash；审核的是旧稿时不能显示新稿已审。
4. 用户正文不静默覆盖，private回归素材不进日志或公共测试fixture。

## 随后补齐的能力

### LF-05 字数控制从“反复测整章”改为可收敛的写作预算

**分类：真实效率与质量问题。**

测量工具已存在，Writer提示词也已有场景预算、结构压缩策略及同稿实测要求（`prompts/builtin-agents/writer.yaml:95`）。`context/processors/measurement_gc.py`还会退役部分旧测量正文，不能报告为完全没有GC。

下一步应在现有生成/修订链路上实施场景预算、合格区间、修订次数和无进展退出；测量结果绑定正文hash，接近边界时局改，明显超长时合并重复场面。保留作者可批准的短章例外，不能截断、填空话或改指标凑达标。

验收同时记录首次长度、各次长度、模型请求数、Token、耗时、事实缺陷和完整性。先得到同模型/同素材/同约束的真实基线，再设改进幅度；本次两个Writer调用不够推出节省百分比或质量提升率。

### LF-06 让用户看到实际生效的模型、文风与检索来源

**分类：现有能力的可观测性缺口与配置可理解性问题。**

- 子Agent模型为空时优先全局default是现有明确设计，见 `runner/subagent_runner.py:158`；无有效记录才继承父模型。应显示实际解析结果及原因，提供明确继承选项时需兼容，不直接把现设计称作模型路由bug。
- Runtime Style Card已在 `context/parts/style_profile.py` 实现。Agent配置、note_read、Skill开关、已确认卡和Token上限均会影响注入。需要显示加载或跳过原因、卡版本及预算，不自动塞完整原始样本。
- Skill清单仅证明可用，不能证明已激活完整规则；`parts/skills.py`与`tools/impls/skill/skill.py`按需架构应保留。
- StoryMemory指纹失效显示stale是正确安全行为；`tools/impls/memory/search_story_memory.py:577`会跳过不新鲜来源。应显示哪些来源被跳过及可用的直接读取途径，提供任务化/增量刷新方案，不能每次保存整书重建，也不能把stale改成ready掩盖问题。

验收要看到实际模型record、已加载Style/Skill摘要、输入源版本、跳过原因、Token分类和索引状态；不展示密钥、完整小说或完整Prompt。已有部分单测不等于本轮运行态已验收。

### LF-07 自然度与章节接口检查接入真实流程

**分类：已存在Prompt/Skill，但实际候选仍反复出现的问题。**

本轮出现重复天气/伤势回顾、人物轮流表愿望、少年统一派工、技术细节压倒人物经验、用总结句快速“治愈”哀伤，以及修理只看空载现象就保证重载能力。应复用 `story-quality`、`narrative-deslop`、`fiction-prose-craft`和现有Reviewer，不继续堆禁词或造第二套去AI系统。

审查目标是叙事功能：人物是否有自己的选择，专业角色是否有独立判断，成果是否被后章承认，情绪是否未经过程跳到下一状态；技术只呈现读者理解行动所需的部分。章节可以延续，也可以硬切，需按时间/地点/目标变化定位，不机械补过渡句。

验收至少覆盖三种不同文风、允许直接情绪与不完整句、不强迫每章冲突/反转/金句；检查相邻章节而非孤立单章。叙述人称/亲属称谓的既有待办继续见 [next-release-narration-quality.md](next-release-narration-quality.md)，不另造重复检测器。

## 本次编排责任与保留的安全能力

1. 41—58章使用Inline custom生成新章是本次私有编排选择。Inline的固定契约是选区改写，且custom不经过Writer的Skill/Style上下文。该用途已停止；现有文本局部改写继续保留，不能据此说Inline所有功能坏了。
2. 59章请求中曾有两个人名/ID错配，但Writer先list后实际按正确name读到了五位同行；错误请求仍需修，不能虚报成实际读错人。
3. 人工短卡的选择与遗漏也影响质量。不能把所有失误归于模型或产品，更不能把临时人工补卡称为产品已修。
4. 本轮写工具审批保持ask、未绕过；真实Writer父子取候选后取消并核正文/设定/状态保护。未观测到AI静默改Canon，不为假设风险宣称已发生数据污染。
5. 未来世界规划关闭、候选不自动确认、索引stale不读旧来源、按需Skill与有界Style Card等已有安全能力应保留。
